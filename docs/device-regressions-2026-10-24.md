# 実機確認で見つかった不具合の修正

対象ブランチ: `codex/security-hardening`

## 解説画像の再編集

Tiptap Imageの既定値は `allowBase64: false`。アップロード・貼り付けで挿入したdata URL画像は表示・保存できても、保存済みHTMLを解析し直すと除外されていた。画像拡張でbase64画像を許可し、親からのHTML再設定では `emitUpdate: false` を指定した。空の内容への切り替えも反映する。

一時的なjsdom環境と実際のTiptap Editor / StarterKit / Imageを使い、埋め込みPNGのHTML読込→保存→エディター作り直し→HTML再設定で画像が保持されること、プログラムからの再設定が変更イベントを発火しないこと、空にすると画像も消えることを確認した。実アプリのファイル選択を使うブラウザー検証は、Chrome拡張のfile URLアクセス制限で実施できなかった。

## ダークモードの表ヘッダー

エディターのダークモード専用CSSで、表の見出し背景に `--text-primary`（明るい文字色）を指定していた。背景用の `--surface-soft` へ修正した。

## クラウド取得が成功・受信0件になる経路

大きな初回送信は、個々の差分バッチではなく全体スナップショットになる。取得側にも既存データがある場合、初回接続時に作られる未送信キューにより全体復元がスキップされ、差分バッチがなければ成功・受信0件になっていた。この経路をメモリー内クラウドと独立した2端末のjournalで再現した。ユーザーの実クラウド内容を読み取って原因を確定したわけではない。

- 復元をスキップして成功にはせず、未送信データにより初回復元できないことを通知する。
- 「端末をバックアップしてクラウドから復元」を追加。置き換え内容を確認し、端末のバックアップを書き出してからクラウドを取得・検証・復元する。
- **端末の未送信変更は自動マージしない。** バックアップに残し、端末内データをクラウドの全体データへ置き換える選択肢である。
- クラウドのハッシュ検証と復元が成功した後にだけ、置き換え前の未送信キューを破棄する。失敗時にはキューを破棄しない。
- 復元後は古い受信コンテキストを再利用せず、スナップショット以降の差分を取得・適用する。
- 通常取得の表示を「全体データを復元」「差分受信」「適用する差分なし」「競合あり」に分ける。
- Google Drive / OneDrive、desktop / mobileの4経路で同じ処理を使用する。

既存の同期履歴があり、そもそも初回スナップショットの取り込み対象ではない場合は、この復元選択肢で過去のデータへ強制的に戻さない。実機で引き続き取得できない場合は、画面の同期状態・未送信件数・競合件数と送受信の順序から別の経路を調べる。

## 検証結果

- 全テスト: 267成功、0失敗。
- 新規テスト: 未送信キューで初回復元が阻まれる再現、明示復元とその後の差分適用、検証失敗・復元失敗でキュー保持。
- lint: エラー0、既存警告8。
- mobile / desktopの本番ビルド: 成功。
- 実アカウントでのGoogle Drive / OneDriveへの送受信・上書きは実施していない。
